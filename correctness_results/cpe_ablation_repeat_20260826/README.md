# CPE KSW 与 BWT-chain 三轮消融实验

## 实验设计

- 平台配置：单节点、单主进程、`cgs_cross + pool`、6 CG / 384 CPE。
- 编译配置：`CPE_PROFILE=1`、`USE_MPI=0`，其余配置完全相同。
- 运行参数：`mem -v 4 -t 1 -1 -I 170,80,500,1`，SAM 写入
  `/dev/null`，排除真实输出 I/O 对 Stage2 的影响。
- 数据：`ERR1203383` PE 子集（75 bp）和 `SRR7963242` PE 子集
  （150 bp）。
- 每个组合运行 3 次，轮换组合顺序并交替数据顺序。表中给出中位数和
  `[min, max]`。

四种编译组合：

| 组合 | FP16 KSW | BWT-chain |
| --- | ---: | ---: |
| baseline | 关闭 | 关闭 |
| ksw_only | 开启 | 关闭 |
| bwt_chain_only | 关闭 | 开启 |
| combined | 开启 | 开启 |

FP16 KSW 使用 32 个物理 FP16 lane，但只使用低半部的 16 个逻辑 lane，
保持原 KSW stripe 宽度和移位语义。

## 结论

1. **FP16 KSW 的局部优化真实存在。** `ksw_only` 将 75 bp 的 mate KSW
   和 forward DP 周期分别降低约 12.3% 和 18.5%；150 bp 日志中约降低
   9.4% 和 16.7%。在 150 bp 上，这兑现为 Stage2 / part3 均约 2.27%
   的墙钟加速。
2. **FP16 KSW 不适合无条件解释成全数据加速。** 75 bp 的 KSW 工作占比小，
   虽然 KSW 子项变快，chain build 却增加约 7.7%，最终 Stage2 退化 2.20%。
3. **BWT-chain 单独开启没有收益。** 它降低了 RID 子项，但没有降低 SA 与
   chain build 总成本；75 bp Stage2 退化 5.41%，150 bp 退化 0.59%。
4. **combined 存在明显非加性交互。** 150 bp 是本轮最好结果，Stage2
   加速 2.98%。75 bp Stage2 虽加速 0.58%，但 part3 仍退化 0.58%；该
   Stage2 小收益主要来自 part5 SAM generation 从约 0.077 s 降至 0.037 s，
   不能归因于 alignment kernel 本身。

因此，当前证据支持保留 FP16 KSW 作为 150 bp 热路径优化；不支持把
BWT-chain 优化单独启用。combined 对测试的两类数据均未使 Stage2 变慢，
但它在 75 bp 上的收益不是 CPE alignment 加速，后续若继续推进，优先考虑
按 read/query 长度选择 KSW backend，并重新拆分验证 BWT-chain 中的 SA
batch、预取和 LDM arena，而不是把三项绑成一个不可解释的总开关。

## 结果文件

- `analysis/runs.tsv`：每次运行的 Stage2、part3 和热点周期。
- `analysis/summary.tsv`：三次运行的中位数、最小值和最大值。
- `analysis/relative.tsv`：中位数及相对 baseline 的百分比。
- `runs/`：24 份完整运行日志。
- `correctness/`：四个二进制的正确性日志和汇总。
- `runs/` 与 `correctness/`：逐轮性能日志和完整输出校验记录；实验结束后
  临时构建、调度脚本已删除，避免继续维护不再使用的组合开关。
