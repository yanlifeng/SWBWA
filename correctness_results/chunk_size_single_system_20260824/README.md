# single + system 下的 chunk size 扫描

## 目的

测量 `-K` 控制的单 CG 输入块大小对 CPE 对齐阶段性能的影响，并据此判断：

- MPI 动态调度的大块是否应继续保持较大；
- 尾部微块缩小到大块的 `1/4` 是否会带来明显的 CPE 性能损失；
- 将所有 MPI chunk 直接缩小到约 4 MiB 是否值得。

## 测试配置

- 代码版本：`30d87222c0f51a55da19ccb0324c034cf979baab`
- 构建：`USE_MPI=0 EXEC_MODE=single CPE_ALLOCATOR=system`
- 运行：`-t 1 -1 -v 4 -I 170,80,500,1`
- `-K`：1、2、4、8、16、32、64 MiB
- 输入：三个数据集的 `_1.fastq_1`，按 SE 处理
- 输出：`/dev/null`
- 调度：所有 21 个作业严格串行提交，均运行在节点 `21622`
- 每个参数点运行一次

三个数据集在所有 chunk size 下处理的 read 数完全一致：

| 数据集 | FASTQ 大小 | read 数 |
| --- | ---: | ---: |
| SRR7963242 | 945,555,584 B | 2,500,000 |
| SRR2496709 | 583,901,384 B | 2,101,235 |
| ERR1203383 | 223,555,584 B | 1,000,000 |

## 指标说明

- `stage2`：完整的“比对并生成 SAM 记录”流水线阶段。
- `part3`：现有主核计时器覆盖的“CPE alignment and SAM length pass”。它最接近本次要观察的 CPE 核心路径，但不是指令级的纯 CPE kernel 计时。
- `part3 平均`：`part3 总时间 / 完成批次数`。块越大，单批处理的数据越多，因此该值自然增大，不能单独用来评价效率。
- `part3 吞吐`：输入文件大小除以 `part3` 总时间，更适合比较不同 chunk size 的 CPE 效率。

完整机器可读结果见 `summary.tsv`。

## 结论

1. 小 chunk 会显著拖慢 CPE 核心路径。与 1 MiB 相比，64 MiB 的 `stage2` 分别加速 `2.47x`、`1.50x`、`1.60x`；`part3` 分别加速 `2.34x`、`1.22x`、`1.31x`。
2. 三个数据集都在 16 MiB 后逐渐进入平台区。32 MiB 相比 64 MiB 的 `stage2` 仅慢约 `2.3%`、`0.5%`、`0.9%`，是更稳妥的吞吐/粒度折中点。
3. 直接把所有大块缩到 4 MiB 不合适。相对 32 MiB，4 MiB 的 `stage2` 在三个数据集上分别慢 `31.7%`、`10.6%`、`14.5%`，SRR7963242 尤其敏感。
4. “主体使用大块，最后 10% 使用大块的 1/4”与结果吻合。例如主体为 32 MiB、尾部为 8 MiB：主体接近吞吐平台，只有有限尾部承担较小块的效率损失，同时提高 MPI 尾部负载均衡能力。
5. 这是一轮单次测量，只用于确定参数量级。若要区分 32 MiB 与 64 MiB 的小幅差异，应对这两个点重复运行至少 3 次并报告中位数。
